### 2026-09-06: Sandboxed tool logic is now decided at generation time
**By:** Backend
**What:** `/api/tools/generate` now runs a dedicated LLM logic-classifier first, then conditionally generates a typed contract plus CommonJS `handler(input)` module, validates it, snapshots it into a Porter sandbox, warms one runtime sandbox, persists the resulting logic metadata on the tool record, and exposes `POST /api/tools/{id}/logic/invoke` for per-tool execution. The validation gate is strict and non-optional: (1) static JS parsing plus source-policy rejection for any import/require, `eval`, `Function`, `process.env`, `process.exit`, `fetch`, `XMLHttpRequest`, or `WebSocket`; (2) a throwaway build sandbox smoke-test with 2-3 representative inputs derived from the generated contract, requiring no crash, completion inside the short exec timeout, and output-schema conformance before snapshot promotion. If any classifier/codegen/validation/promotion step fails, generation soft-falls back to the existing static/client-side HTML path and records a warning instead of failing the whole tool build.
**Why:** I chose a safety-first sequencing model instead of fully parallel HTML + logic promotion. The HTML generator needs the actual generated contract and invoke-path shape to wire the UI correctly, and a validation failure must never leave us shipping HTML that depends on a missing backend. So the pipeline does cheap classification plus compact logic codegen early, caps sandbox promotion with explicit remaining-budget math, and falls back immediately when logic work would eat into the core HTML budget. That keeps the new capability within the existing 280s target while preserving the project rule that enhancements must never break the core generation path.
